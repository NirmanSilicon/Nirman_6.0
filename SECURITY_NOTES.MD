# SECURITY_NOTES.md — Cryptographic Privacy Boundaries & Key Management

This document defines the security architecture, privacy invariants, cryptographic boundaries, and production key management guidelines for the AXYRA Zero-Knowledge & Blockchain Verification Layer.

---

## 1. Zero-Knowledge Privacy Invariant: What is Proven vs. What Stays Hidden

The core design goal of AXYRA's ZK scoring layer is to allow satellite operators to cryptographically certify causal failure verdicts to third parties (insurers, manufacturers, launch providers, regulators) without revealing proprietary or mission-sensitive telemetry metrics.

### 1.1 Private Witness Inputs (Hidden from External Parties)
These values are inputs to the Circom witness calculation and are **never** included in public signals, smart contract call data, API responses, or request logs:

| Input Variable | Description | Security / Business Sensitivity |
|---|---|---|
| `s_temporal` | Temporal precedence score ($0.0 \dots 1.0$) scaled by $10^6$ | Reveals exact telemetry gap and propagation speed |
| `s_dependency` | Subsystem coupling strength ($0.0 \dots 1.0$) scaled by $10^6$ | Discloses internal subsystem topology & electrical architecture |
| `s_intermediate` | Intermediate event consistency ($0.0 \dots 1.0$) scaled by $10^6$ | Exposes telemetry channel existence and monitoring sensitivity |
| `salt` | 248-bit cryptographic blinding factor | Prevents rainbow-table or brute-force pre-image attacks on Poseidon commitment |

### 1.2 Public Signals (Publicly Disclosed & Verified On-Chain)
Only these 6 scalar field elements are published and verified on-chain or by downstream verifiers:

| Signal Index | Field Name | Description | Rationale |
|---|---|---|---|
| `publicSignals[0]` | `verdict_confirmed` | Boolean flag ($1$ = Confirmed, $0$ = Not confirmed) | The binary verdict required for insurance payout / sign-off |
| `publicSignals[1]` | `w_temporal` | Temporal precedence weight ($47,500 = 0.0475$) | Standard ensemble consensus weights published in calibration spec |
| `publicSignals[2]` | `w_dependency` | Dependency topology weight ($632,000 = 0.6320$) | Published consensus weight |
| `publicSignals[3]` | `w_intermediate` | Intermediate consistency weight ($320,500 = 0.3205$) | Published consensus weight |
| `publicSignals[4]` | `threshold` | Minimum confidence threshold ($400,000 = 0.40$) | Standardized policy threshold |
| `publicSignals[5]` | `private_input_commitment` | Poseidon hash of private witness | Binds proof to specific satellite telemetry without revealing values |

## 2. Cryptographic Salt & Commitment Handling

### 2.1 Blinding Factor Generation
Because the domain of feature scores is bounded ($0 \le S \le 1,000,000$), an attacker who knows the formula could precompute all $10^{18}$ combinations of $(S_T, S_D, S_I)$ if unblinded.
To prevent dictionary attacks:
- Every commitment generated by `generate_commitment` draws a cryptographically secure 248-bit random integer (`ethers.randomBytes(31)`).
- The salt is passed alongside the private scores into the 4-input Poseidon hash function.
- The salt is strictly discarded after proof generation or stored only in local secure hardware storage (e.g. onboard secure enclave).

### 2.2 Logging Redaction Middleware
To ensure zero accidental leakage in server logs:
- `zk_chain_service/src/middleware/redactLog.ts` intercepts all Express incoming requests and sanitizes request bodies.
- Any field named `s_temporal`, `s_dependency`, `s_intermediate`, `salt`, `privateKey`, or `secret` is replaced with `[REDACTED_FOR_ZK_PRIVACY]` before writing to stdout, log files, or telemetry sinks.

## 3. Trusted Setup Ceremony & Curve Parameters

### 3.1 Curve Choice: BN128 (Alt-bn128 / bn254)
- Supported natively by Ethereum and EVM-compatible chains (Polygon, Arbitrum, Base) via precompiled contracts `ecAdd` (0x06), `ecMul` (0x07), and `ecPairing` (0x08).
- Provides approximately 100–128 bits of security.

### 3.2 Powers-of-Tau Ceremony
- **Development Mode**: Single-contributor ceremony with local entropy contribution implemented in `scripts/setup_ceremony.ts`.
- **Production Recommendation**:
  - For production mainnet deployments, utilize the Hermez / Perpetual Powers-of-Tau ceremony files (e.g. `powersOfTau28_hez_final_14.ptau`), which have hundreds of independent contributors.
  - Execute a multi-party Phase 2 ceremony for `causal_verdict.circom` with independent satellite manufacturer, space agency, and insurer participants.
  - Discard the toxic waste entropy ($\tau$) immediately after zkey finalization.

## 4. Key Management Guidelines for Production

### 4.1 Demo vs. Production Key Separation
- The default `.env` and hardhat configuration use well-known Hardhat demo accounts (`0x7099...`, `0x3C44...`, `0x90F7...`, `0x15d3...`) solely for reliable automated local tests.
- **NEVER** use demo private keys on public testnets or mainnet.

### 4.2 Production Multi-Sig Architecture
For production operations on Polygon / Ethereum:
1. **Hardware Security Modules (HSM)**: Operator and manufacturer signing keys should be held in FIPS 140-2 Level 3 HSMs or cloud KMS (e.g., AWS KMS / Google Cloud KMS) with strict IAM policies.
2. **Account Abstraction (ERC-4337) / Gnosis Safe**: Wrap stakeholder addresses into Safe multi-signature smart accounts requiring $M$-of-$N$ internal approvals before signing off on `MultiSigSignOff.sol`.
3. **Parametric Insurance Escrow**:
   - `ParametricPolicy.sol` holds funds in escrow. Ensure the contract is audited for re-entrancy and integer safety.
   - Emergency recovery: Insurer withdrawal functions should have timelocks (e.g. 48-hour delay) to protect policyholders from flash withdrawals during active incidents.
